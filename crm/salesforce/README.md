# Salesforce

Automation inside a Salesforce org: an Apex action that Flow can call, a queued
callout to an external service, and a batch job that repairs data on a schedule.

**This runs free.** A [Developer Edition org](https://developer.salesforce.com/signup)
is permanent and costs nothing, and it includes Apex, Flow, the Bulk API and a
full sandbox of the objects used here. You do not need a paid licence to run any
of this.

```
force-app/main/default/classes/
├── HygieneRules.cls                the rules, with no SOQL and no DML
├── HygieneRulesTest.cls
├── LeadHygieneAction.cls           @InvocableMethod, called from Flow
├── LeadHygieneActionTest.cls
├── LeadEnrichmentQueueable.cls     callout, chained, with a depth guard
├── LeadEnrichmentQueueableTest.cls
├── LeadHygieneBatch.cls            Database.Batchable, scheduled weekly
└── LeadHygieneBatchTest.cls
```

There is no Flow metadata file here on purpose. Flow XML is generated by the
builder and is unpleasant to hand-edit or review, so the Flow is three clicks in
the UI: a record-triggered flow on Lead create, an **Action** element pointing at
**Clean a Lead**, and the record variable passed in. The Apex is the part worth
keeping under version control.

## The division of labour

Salesforce has four automation tools and the usual failure is picking the wrong
one, not misusing the right one.

| Use | For | Not for |
| --- | --- | --- |
| **Flow** | Orchestration, branching, screens, anything an admin should own | Loops over thousands of records, callouts with retry logic, anything needing a unit test |
| **Apex invocable** | The logic Flow cannot express, exposed as one Flow action | Things Flow already does well. An invocable that only sets a field is a step backwards |
| **Queueable** | Callouts, and work that must happen after the transaction commits | Anything the user is waiting on |
| **Batch** | More records than a single transaction can hold | Small volumes. A batch over 50 records is overhead |

The example uses all four for the parts each is good at: a Flow catches the Lead,
hands the record to an invocable for the rules Flow cannot express, the invocable
queues a callout, and a weekly batch repairs the records that were created before
any of this existed.

## Bulk safety is the whole game

Every governor limit problem in Salesforce is the same bug: something that works
on one record runs once per record. Three rules, and every class here follows
them.

**1. An invocable takes and returns a `List`.** That is not a convention, it is
the signature Salesforce requires, and it exists to force bulk thinking. Flow
calls the method once with 200 records, not 200 times with one.

**2. No SOQL and no DML inside a loop.** `HygieneRules` is deliberately a class
with neither. It takes records, returns changed records, and has no idea a
database exists. That makes it unit-testable without `@isTest(SeeAllData=true)`
and impossible to write a query into by accident.

**3. The order of the output list must match the order of the input list.** Flow
matches results to records positionally. Returning a filtered list silently
assigns the wrong result to the wrong record, and nothing errors.

## Running it

```bash
sf org login web --alias dev
sf project deploy start --source-dir force-app --target-org dev
sf apex run test --target-org dev --code-coverage --result-format human
```

Salesforce requires 75% coverage to deploy to production. The tests here cover
the bulk path (200 records), the single-record path, and the failure path,
because a test that only proves the happy path on one record is how a class
passes deployment and fails on the first real import.

## The callout pattern

`LeadEnrichmentQueueable` shows three things that are easy to get wrong:

- **`Queueable implements Database.AllowsCallouts`.** You cannot call out from a
  trigger context. Queueing is the standard way around it, and it also means the
  callout happens after the transaction commits, so a rollback cannot leave you
  having told an external system about a record that no longer exists.
- **A chain depth guard.** A queueable that enqueues itself will run until it
  hits the stack-depth limit. The class carries `depth` and stops, rather than
  relying on the platform to stop it.
- **`Limits.getLimitCallouts()` checked before each call**, so a batch that runs
  out of callouts reports which records were not enriched rather than throwing
  halfway and losing the record of what was done.

## Prior art

`@InvocableMethod` and `@InvocableVariable` are Salesforce's documented bridge
between Flow and Apex, and the `List` in, `List` out signature is required by the
platform rather than chosen here. See the Apex Developer Guide on
[InvocableMethod](https://developer.salesforce.com/docs/atlas.en-us.apexcode.meta/apexcode/apex_classes_annotation_InvocableMethod.htm)
and Salesforce's own bulkification guidance. The implementations in this
directory are written for this repository.
